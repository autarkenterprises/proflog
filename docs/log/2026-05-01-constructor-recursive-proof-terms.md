# Constructor-Recursive Proof Terms and Integration Path

Date: 2026-05-01
Branch: `main`

## Context

The intensified list-family matrix now has answer rows that close through
ADR-0033 structural residual completion. The heavier
`append-inverse-flat-longer` probe also closes all five split answers for
`append(x, y, [a,b,c,a])` at a higher raw limit.

The question raised after that probe was whether these heavier rows produce
associated proofs or only answer bindings.

## Current Behavior

They are proof-search backed and proof-bearing internally, but the matrix probe
CLI reports only answer-level summaries.

The ordinary raw answer path asks `program-raw-answer-states` for raw kernel
states. Each raw state includes:

- answer-variable state;
- substitution state;
- disequality state;
- residual formulas; and
- a kernel proof term.

`export-answer-record` projects each raw state into an answer record with
`:bindings`, `:residuals`, and `:proofs`. ADR-0033's structural completion hook
may then call the constructor-recursive layer to discharge structurally safe
negative defined-call residuals. When that succeeds, the completed record keeps
the original proof evidence and appends a constructor-recursive residual
settlement proof.

The list-family matrix's `run-case` then discards proof detail from its printed
result, keeping only counts, target status, and closed bindings. This is why
the CLI output looks answer-only even though the internal records retain proof
evidence.

## Why These Proofs Are Still Prototype Terms

The constructor-recursive layer emits tagged trees such as:

```clojure
(constructor-recursive ...)
(constructor-recursive-call ...)
(constructor-recursive-alt ...)
(constructor-recursive-guard ...)
(constructor-recursive-residual-settlement ...)
(cr-bind)
(cr-decompose ...)
```

These terms are meaningful operational certificates for the sidecar layer.
They record which guarded alternative was chosen, how equality guards unified,
how constructor arguments decomposed, and how a deferred residual call was
settled.

They are still prototype proof terms because they are not yet:

- part of a single ordinary kernel proof grammar;
- independently checkable by a proof verifier for the original query;
- generated by the central `close-agendao` proof relation;
- stable as public API artifacts; or
- normalized into the same proof vocabulary as tableau steps such as `split`,
  `conj`, `univ`, `witness`, `eq-step`, and guarded procedure-call closure.

The current invariant is therefore engineering-level rather than final
proof-object-level: the sidecar proof justifies a generic structural descent
used to complete an answer record, but it has not yet been absorbed into the
ordinary kernel proof calculus.

## Deeper Integration Steps

1. Specify the proof boundary.

   Define exactly what a constructor-recursive settlement proof certifies:
   given a program, exported bindings, and a residual frontier, it proves that
   the residual frontier can be discharged while refining only the branch-local
   substitution state. This should be written as a small proof grammar and an
   invariant for `constructor-recursive-residual-settlement`.

2. Add a proof checker for constructor-recursive terms.

   Before merging the sidecar into the kernel, add a deterministic checker that
   validates constructor-recursive proof terms against a compiled program and
   an initial record. The checker should cover non-list constructor recursion,
   representative reverse rows, and inverse append rows. This gives the
   sidecar proof format a validation point while it is still separate.

3. Expose proof diagnostics in the matrix probe.

   Add an opt-in mode that prints proof-root counts, proof-step signatures, or
   a bounded proof sample for answer rows. This should mirror
   `query-answer-diagnostics` and avoid making ordinary matrix output noisy.

4. Move residual completion earlier than exported-record reconstruction.

   The long-term path should not reconstruct branch context from exported
   records. Residual completion should run while the raw answer path still has
   substitution, disequality, residual, fuel, call-depth, answer-variable, and
   proof metadata in scope.

5. Re-express guarded constructor descent as an ordinary answer-overlay rule.

   Introduce a proof-producing relation in the ordinary raw answer path that
   consumes the same guarded-clause IR but returns ordinary raw answer state:
   refined substitution, disequalities, residuals, remaining fuel, and a proof
   subtree. This is the key step that makes constructor-recursive completion a
   kernel/answer-path capability instead of a post-export sidecar.

6. Normalize proof vocabulary.

   Replace or wrap `constructor-recursive-*` tags with ordinary proof tags or a
   documented background-step tag analogous to the existing profiled kernel
   layers. The result should be traversable by existing proof utilities and
   should not require consumers to understand a separate proof dialect.

7. Keep diagnostics and opt-out paths.

   ADR-33 currently preserves diagnostics that expose unresolved raw frontiers.
   That should remain available while deeper integration happens, so tests can
   distinguish "the raw kernel produced this frontier" from "the integrated
   structural rule completed it."

8. Retire the sidecar only after parity.

   Once the ordinary raw answer path can close the same rows with ordinary proof
   evidence, keep `proflog.kernel.constructor-recursive` as a compatibility
   diagnostic for one transition, then either delete it or reduce it to a thin
   wrapper around the integrated rule.

## Recommended Sequence

The least risky next development sequence is:

1. Add proof-sample diagnostics to the list-family matrix.
2. Add a constructor-recursive proof checker.
3. Move settlement from post-export records to raw answer-state context.
4. Convert the sidecar descent into an answer-overlay relation.
5. Promote checked proof terms into the ordinary proof vocabulary.

This keeps each step testable and avoids losing the current passing behavior
while making the proof evidence progressively less provisional.
