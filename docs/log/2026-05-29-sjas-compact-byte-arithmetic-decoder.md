# SJAS Compact Byte Arithmetic Decoder

Date: 2026-05-29
Branch: `adr-0073-sjas-correspondence-program`

## Track 1 Slice

This Track 1 code-format/arithmetic slice removes the generated host lookup
table used to interpret byte arguments of compact public `code-N` terms.

Previously, compact code byte terms were decoded by checking whether the whole
ground term occurred in a precomputed Clojure table of the 64 canonical byte
numerals. That preserved generated-code behavior, but it was still nominal
matching over host data rather than arithmetic interpretation of the public
U-Grounding numeral placed in the code term.

The compact byte reader now parses the supplied byte argument through its
public `0`/`1`/`dbl`/`add(_,1)` numeral shape and then relates the resulting
bits to a base-64 byte. The parser is shape-directed with `conda`, so ground
compact code terms remain tractable while noncanonical but arithmetically
equivalent byte numerals are accepted.

## Red/Green Evidence

The focused regression
`sjas-compact-code-byte-reader-interprets-byte-numerals-arithmetically` writes
the one-byte formula code for `true` as:

```text
code-1(add(dbl(0), 1))
```

This denotes byte `1` arithmetically, but it is not the generated canonical
byte term `(1)`.

Before the change, `wff(code-1(add(dbl(0), 1)))` failed because the byte reader
only matched against generated canonical byte terms. The source audit also
failed on `code-byte-term->byte` and `code-byte-term-entries`.

After the change, the noncanonical-byte `wff` check passes and the audit shows
that the generated byte lookup table is gone.

## Tractability Note

The first implementation ordered the relation as "enumerate byte bits, then
parse the term." That made the slow structural theorem-code selector exceed
its timeout. Reordering the relation to parse the supplied ground numeral first
and using a shape-directed parser restored tractability without restoring the
host lookup table.
