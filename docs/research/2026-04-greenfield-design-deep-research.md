# Greenfield Design for Proflog

## Design stance and non-negotiable decisions

This implementation should be built as a **purity-first extension of αleanTAP**, not as a retrofitted Prolog engine. Fitting’s Proflog is a language of **full first-order formulas with equality**, not Horn clauses, and its operational semantics are given by **tableau proof search plus one additional branch-closing rule**, the Procedure Call Rule. αleanTAP is the right substrate because it already represents tableau proving as a **pure relation** with **no mode restrictions**, can prove ground formulas, generate non-ground theorems, and accept non-ground proofs; core.logic explicitly positions itself as a miniKanren-derived system with **nominal logic programming** and **constraint logic programming** support, including αKanren and cKanren-style extensions. citeturn41view0turn41view2turn11view0turn44view0turn37view0turn37view2

The greenfield implementation should therefore make five decisions up front. First, the **trusted semantic target** is Fitting’s language and supervaluation-based success/failure notion for **ground literals**. Second, the implementation should extend that target to **open queries** using free-variable tableaux, because Fitting explicitly says free variables are what make “familiar Prolog style” querying possible, while warning that answers must be restricted to terms of the original language `L`, not the enlarged Skolem language. Third, the kernel should remain **purely relational** unless a later, isolated optimization layer proves unavoidable. Fourth, equality should be implemented as **free-constructor term equality** over the Herbrand-style term language, not by ad hoc host-language rewriting. Fifth, the implementation should require an **explicit language declaration** and enforce it, because Fitting’s soundness argument depends on fixing `L` and forbidding proof-introduced symbols from leaking into user answers. citeturn42view0turn41view0turn41view1turn41view2turn31view2

The existing `autarkenterprises/proflog` repository is useful as precedent, but not as authority. It already contains separate Clojure sources for equality and procedure-call variants, a design note, and a large test suite organized around equality, recursive procedure calls, mutual recursion, Fitting’s `P1` even/odd program, Fitting’s `P2` Nim program, soundness guards, disunification, arithmetic, and universally quantified specifications. That is evidence of the right pressure points, but the design below re-derives the architecture from Fitting, αleanTAP, and miniKanren rather than inheriting repo-local implementation choices. citeturn17view0turn18view0turn25view0turn25view1

## Formal model and surface language

The user-facing language should follow Fitting, not leanTAP’s Skolemized input format. A Proflog program lives in a fixed first-order language `L` consisting of constants, function symbols, relation symbols, and equality; formulas may use `∧`, `∨`, `¬`, `⊃`, `∀`, `∃`, `true`, and `false`. An `L`-clause has the form `R(x1,...,xn) ← φ(x1,...,xn)`, and an `L`-program contains **at most one clause per non-equality relation symbol**. Fitting’s paper defines queries as **ground literals of `L`**, and the semantics are three-valued: a query may succeed, fail, or remain neither if neither tableau closes. citeturn41view0turn41view1turn41view2turn5view5

The greenfield implementation should preserve that model exactly at the semantic boundary, while offering **surface sugar** for ergonomics. In particular, multiple user clauses for the same relation should be accepted only as frontend sugar and desugared into Fitting’s single-clause form by **α-renaming variables and disjoining bodies**. That preserves the intended reading of multiple clauses as disjunction while still compiling to a program shape that matches Fitting’s formal restriction and the Procedure Call Rule. Language declarations should be mandatory, because Fitting is explicit that tableau-introduced symbols cannot appear in query answers and that fixing `L` is part of the soundness story. citeturn41view0turn41view1turn41view2

Internally, the prover should use the **tagged αleanTAP style of syntax**, because that representation was introduced specifically to eliminate overlapping cases and keep the prover declarative. The greenfield core should extend that grammar with `exists`, `eq`, `neq`, and a rigid parameter form for δ-witnesses. αleanTAP’s dissertation chapter gives the rationale for tagging formulas, literals, applications, and variables; the current experimental Proflog repo independently converged on the same idea for `pos`, `neg`, `eq`, `neq`, `app`, `var`, and `par`. citeturn43view3turn44view0turn38view3turn39view0

A good core grammar is:

```clojure
Formula ::= ['true]
          | ['false]
          | ['and Formula Formula]
          | ['or Formula Formula]
          | ['forall (tie Nom Formula)]
          | ['exists (tie Nom Formula)]
          | Literal

Literal ::= ['pos Atom]
          | ['neg Atom]
          | ['eq Term Term]
          | ['neq Term Term]

Atom    ::= ['app RelSymbol Term*]

Term    ::= ['var Nom]          ; object-language bound variable reference
          | ['app FunSymbol Term*]
          | ['par Nom]          ; rigid δ-parameter, internal only
          | <host logic var>    ; meta-level unknown for open queries/synthesis
```

Object-language variables should remain **nominally bound names** referenced by `['var a]`, while user query holes and synthesis targets should be **host miniKanren logic variables**, exactly as in αleanTAP. That separation is one of the reasons αleanTAP can run forward, backward, and partially guided without collapsing object-language binding into host-language mutation. citeturn11view0turn44view0turn37view1turn45view3

## Proof kernel and operational semantics

The kernel should be a single relational prover, conceptually of the form `proveo(formula, unexpanded, literals, env, program, proof)`, because that is the αleanTAP pattern and it maps directly onto Fitting’s tableau rules. The `unexpanded` stack holds formulas still to be processed on the current branch; `literals` holds branch literals; `env` maps nominally bound object variables to current instantiations; `program` is the compiled Proflog program; and `proof` is a structured proof object for debugging, proof checking, and partial proof guidance. αleanTAP’s key insight is that the tableau process itself can be represented as a relation between formulas and their tableaux, and the final implementation should preserve that. citeturn11view0turn44view0turn15view2turn14view3

Formula normalization should be implemented as a **relational `negateo` and NNF converter**, not as a one-way prepass. αleanTAP’s backward-running examples are valuable precisely because normalization and proof search remain relational. The kernel may store formulas in a restricted tagged NNF form for efficiency, but the normalization relation itself should still support forward use, reverse use, and partial synthesis. This is important because negative procedure calls require constructing `¬φ(t)` relationally, not by a host-language helper that only works in the forward direction. citeturn43view1turn44view0turn24view5turn25view2

Universal and existential quantifiers should be handled directly, not by global Skolemization. Fitting’s own implementation notes say that classical tableaux are not directly automatable as written because γ can introduce arbitrary closed terms, and that automation typically replaces this with **free variables plus later unification**, while δ must be handled with Skolemization or run-time Skolemization. αleanTAP already supplies the free-variable γ strategy; Proflog should add the dual δ rule by introducing a fresh rigid nominal parameter `['par p]` that is scoped to the branch and never exported to the user. This preserves the paper’s operational picture much more faithfully than a fully Skolemized surface language would. citeturn42view0turn38view3turn37view1turn45view3

The Procedure Call Rule should be implemented exactly in branch-closing position. On a positive literal `R(args)`, look up the unique clause for `R`, bind formal parameters to the current arguments, and try to close a **fresh subsidiary tableau** for the instantiated body `φ(args)`. On a negative literal `¬R(args)`, negate the instantiated body relationally and try to close a fresh subsidiary tableau for `¬φ(args)`. The subsidiary tableau must have fresh `unexpanded` and `literals` structures, because Fitting’s soundness discussion depends on that isolation, but it should still share the surrounding logic-variable state so that successful subsidiary proofs can instantiate open query variables. That's the crucial bridge from theorem proving to logic programming. citeturn5view4turn5view5turn19view1turn39view0

At the top level, query evaluation should expose **two semidecision procedures**, not pretend to solve three-valued semantics outright. Fitting defines success by a closed tableau for `¬A` and failure by a closed tableau for `A`; some queries satisfy neither condition. Therefore the runtime should expose `succeedso` and `failso` as relations, and a convenience API should run them in a **fair interleaving race**, returning `:succeeds`, `:fails`, or `:undetermined-within-budget`. That is operationally honest: it does not conflate “not yet found” with semantic `⊥`, but it still matches the paper’s notion that a query may legitimately be neither successful nor failing. core.logic’s interleaving search strategy makes this a much better fit than Prolog’s depth-first search. citeturn5view5turn41view3turn31view0turn31view4

## Equality and the purity envelope

The strongest, cleanest greenfield choice is to implement Fitting’s equality layer as **unification plus disequality constraints over free-constructor terms**, not as an explicit bespoke paramodulation engine. In Fitting’s weak Herbrand models, Free Closure expresses constructor clash, One-One expresses injectivity, and Substitutivity expresses replacement under equality. On a tagged constructor term language, those are exactly the phenomena that syntactic unification and disequality already capture: `eq(t,u)` reduces to a unification problem, `neq(t,u)` reduces to a disequality problem, clash fails immediately, same-head equalities decompose structurally, and substitutions propagate equalities through all branch literals automatically. core.logic already exposes complex-term disequality via `!=`, and its term types include occurs-check support; the API even distinguishes normal `run` from `run-nc`, which explicitly disables occurs-check. Proflog should use the former and never the latter in the proof kernel. citeturn6view0turn37view2turn45view0turn45view3

This design is materially better than re-implementing Fitting’s equality rules as manual branch rewrites. The current experimental repository demonstrates exactly where a direct-rule implementation starts to bend toward impure host inspection: it uses `project` for term-shape dispatch in substitution and again for a groundness-style admissibility check around procedure calls. That is useful evidence, but it is also the place where a greenfield implementation should improve. A clean kernel can avoid `project` by using only **tag-driven relational patterning** and core.logic’s native substitution/constraint store. In other words, tagged syntax should do the shape discrimination, and equality should ride on the host relation engine rather than competing with it. citeturn38view0turn38view1turn38view2turn43view3turn44view0

The tricky case is not positive equality; it is **negative equality with free variables**. Fitting warns that once free variables are admitted, disunification becomes central, that there can be infinitely many disunifiers, and that generating and merging them may be the hardest implementation problem. The right greenfield response is **not** to eagerly enumerate disunifier streams in milestone one. It is to preserve purity by storing negative equalities as **symbolic disequality constraints** and to enumerate concrete constructor refinements only when the surrounding search demands them. That keeps the kernel declarative, fits naturally with miniKanren/cKanren-style constraint execution, and gives a principled way to return partially constrained answers instead of pretending the disunifier space must always be fully exploded. citeturn42view0turn36search1turn36search2turn37view2

The exported-answer discipline should be stricter than the branch discipline. Fitting explicitly says that if free-variable procedure calls instantiate a variable to a term `t`, then `t` must be a term of the original language `L`, not of the Skolemized enlargement. Accordingly, the kernel may internally use `['par p]` for δ-witnesses, but the API should only return substitutions whose reified terms are **parameter-free `L`-terms** or, in synthesis modes, partially specified terms with residual disequalities but still no `par` constructors. This should be enforced by a pure structural admissibility relation, not a host-language filter. If performance later forces a host-level post-filter for usability, that impurity must remain at the API boundary, never in `proveo` or its immediate support relations. citeturn42view0turn41view0turn41view1turn31view2

Operational compromises are acceptable only under a written policy. Fitting says an incomplete but efficient mechanism can be acceptable if the sources of incompleteness are well understood. That suggests a two-profile design. The default profile should be **semantic and pure**, with fair search, symbolic disequalities, and no committed choice. A later optional profile may add bounded γ-agendas, memoization, or tabled procedure calls for speed, but every such optimization must be documented as either semantics-preserving or as a source of incompleteness. The implementation should never smuggle in `cut`, `project`, or non-relational arithmetic and later describe that as “still Proflog.” citeturn42view0turn31view2turn45view0

## Architecture and development roadmap

The codebase should be split into a small number of semantic modules with a single executable kernel. A sensible namespace layout is: `proflog.language` for declarations and arity checks; `proflog.ast` for constructors and printers; `proflog.normalize` for relational negation and NNF conversion; `proflog.subst` for nominal substitution; `proflog.kernel` for tableau search; `proflog.program` for clause lookup and head/body binding; `proflog.query` for status racing and answer packaging; and `proflog.proof` for proof-term shapes and proof checking. That architecture mirrors αleanTAP’s decomposition into formula representation, substitution, and proving, while making room for the Proflog-specific additions of δ-witnesses, equality, and procedure calls. citeturn15view1turn15view2turn44view0turn39view0

**Phase Alpha** should rebuild a minimal αleanTAP-like kernel from the primary sources before any Proflog work begins. The exit criterion is a pure relational prover for tagged first-order formulas with conjunction, disjunction, universal quantification, and complementary literal closure, together with proof objects and backward-running examples. This phase exists so that later failures can localize cleanly to “equality” or “program calls,” instead of being confounded with baseline tableau behavior. citeturn11view0turn44view0turn43view1

**Phase Equality** should add direct existential support and branch-local Herbrand equality. The exit criterion is that `eq` and `neq` behave correctly under constructor clash, constructor injectivity, congruence, disequality propagation, and occurs-check, all without kernel impurity. This phase should intentionally avoid any manual rule system that duplicates what core.logic’s substitution and constraint store already provide. The future arithmetic extension depends on this remaining a genuinely relational substrate, because the arithmetic literature that grew out of miniKanren emphasizes exactly the value of mode-free, pure relations over unrestricted non-logical arithmetic operators. citeturn6view0turn37view2turn33view0

**Phase Calls** should add the Procedure Call Rule and three-valued query APIs. The exit criterion is that Fitting’s `P1` and `P2` work end-to-end, that positive and negative procedure calls both close branches correctly, that success and failure are discovered by interleaving search over `A` and `¬A`, and that undefined examples are exposed honestly as unresolved within the semantic race. This phase should also add the mandatory language declaration and the compiler pass that desugars multiple surface clauses into Fitting form. citeturn41view1turn41view2turn5view4turn5view5turn41view3

**Phase Answers** should then lift the engine to programmer-facing evaluation. The exit criterion is a user API that returns a lazy stream of answer records, each containing at least a restricted substitution for the query variables, a proof term, and any residual disequalities. This is also the phase where backward modes become first-class: partial query completion, theorem generation, and limited clause-body synthesis should all function, because preserving αleanTAP’s mode freedom is one of the central reasons to build on it in the first place. citeturn11view0turn43view1turn44view0turn39view0

**Phase Optimization** should be explicitly optional and semantically downstream. Only after the pure kernel passes the full suite should the project consider tabled goals, memoized procedure calls, or agenda heuristics for γ-expansions. miniKanren’s interleaving search already avoids some forms of divergence that plague depth-first systems, but Byrd’s dissertation is equally clear that fair search does not abolish divergence and that tabling solves additional classes of programs. That makes tabling an appropriate later optimization, not a prerequisite for a correct first implementation. citeturn31view0turn31view4turn45view0

## Test strategy and flagship programs

The project should adopt **strict red-green TDD** as a release gate, not as an aspiration. Every semantic rule gets introduced only after a failing test exists for it, and every phase must include both **micro-tests** for single relations and **end-to-end tests** that exercise the public query API. The current experimental repository is right to organize tests by semantic area instead of by file; a greenfield suite should do the same, with sections for normalization, quantifiers, equality, procedure calls, recursion, undefined behavior, backward modes, and performance regression. citeturn25view0turn25view1turn22view1

The most important tests should be semantic, not just structural. For procedure calls, the foundational property is Fitting’s Proposition 7.7: for any ground instance of a program clause, the truth value of `R(t)` matches the truth value of `φ(t)`. A bounded property-testing harness should therefore generate small ground terms of the declared language and assert, for every sample program used in the suite, that `query-succeeds?(R(t))` iff `query-succeeds?(φ(t))`, and similarly for failure. That is the fastest way to catch unsound interleavings between clause lookup, body instantiation, negation, and subsidiary tableaux. citeturn7view0turn42view0

The flagship end-to-end programs should deliberately emphasize what Proflog can express that Horn-clause Prolog cannot express as directly. The first two are Fitting’s own: `P1` even/odd, where `odd` is defined with a universal implication in the body, and `P2` Nim, where `win` depends on existential choice plus negation. Those are not merely regression examples; they are canonical evidence that the language is about **full first-order definitions with recursion**, not Horn rules plus a few extras. citeturn41view1turn41view2turn8view2

Beyond Fitting’s examples, the suite should include at least three “uniquely Proflog” program families. One should define **undefinedness** directly, for example `p ← ¬p`, to validate the three-valued operational interface. One should define an **extensional property** such as subset or set equality using universal quantification and equality, because these are much more natural in Proflog than in Horn-clause encodings. One should define a **global specification** like sortedness or uniqueness using a quantified body over a structural relation such as `member`, `adjacent`, or `lt`, again to demonstrate why having unrestricted first-order formulas in clause bodies matters. The current repo’s test inventory already points in this direction with sections for sorted predicates, subset relations, transitive closure, and arithmetic; the greenfield version should keep those as milestone tests, but tighten them into truly language-defining examples. citeturn25view0turn25view1turn26view4turn33view0

Finally, the arithmetic roadmap should start in the tests before it reaches the implementation. The equality milestone should already include “arithmetic-adjacent” symbolic examples over Peano terms, because later work is intended to add fully relational arithmetic rather than host-language arithmetic operators. The relevant miniKanren arithmetic literature is explicit that relational arithmetic should avoid non-logical operators and mode restrictions; that future goal is much easier to preserve if the Proflog equality layer, answer discipline, and proof kernel are already pure and constructor-based. citeturn33view0turn32search14

This roadmap is the defensible line: **exact Fitting semantics for the ground core, αleanTAP-style relational proof search for lifted use, equality implemented through pure unification and disequality over free constructors, mandatory language declarations, no impure kernel operators, and every deviation from completeness isolated and documented as an explicit runtime profile rather than hidden in the semantics.** citeturn41view0turn42view0turn44view0turn31view2
